### 1.2 What the poll engine actually is

`poll_server.c` is 129 lines and contains nothing except the poll-specific event loop. Everything else — sockets, the request/response state machine, the transport, the statistics, the CLI and the shutdown path — belongs to the shared framework. This is the arrangement the other three engines use too, and it is the reason the four engines can be compared fairly.

The shape of the engine:

- **A `table_t` with two parallel arrays.** `fds[]` is the `struct pollfd` array handed straight to `poll()`; `clients[]` holds the `conn_t *` that owns each entry. Entry *i* of one array and entry *i* of the other describe the same connection, so going from a ready descriptor to its connection is O(1).
- **Slot 0 is always the listening socket.** It is armed `POLLIN` for the whole life of the process. Clients occupy slots 1..count-1, and every client is appended with `POLLIN`, because every client starts by reading a request header.
- **Interest is rebuilt every iteration.** Before each `poll()`, every client's `events` field is set from its framework state: `POLLIN` while the connection is reading (HEADER / RECEIVE), `POLLOUT` while it is sending (SEND). Never both.
- **Removal is O(1).** When a connection dies, the last entry of the table is moved into its slot and `count` is decremented, instead of shifting every later entry down.
- **UDP is a separate, much smaller path.** UDP has no per-client sockets, so `run_udp()` polls a single `struct pollfd` for the listener and hands the datagrams to the framework's `udp_drain()`.
- **The engine only counts.** Every `poll()` call increments `s->loop_calls` and `s->sc_wait`, so poll's syscall cost lands in the same counters as the other three engines.

## 2. Freebuff — the engine

### 2.1 How I used it

Freebuff (Codebuff, DeepSeek V4 Flash) was the only AI tool used for this component, and it did four jobs: it built my understanding of the mechanism, it **wrote the engine** (section 2.2), it found the integration problem (section 3), and it produced the comments and the README (sections 4 and 5).

I used it in short sessions: first to build the mental model of `poll()` and of the framework contract, then to implement the engine against that contract, then to review the parts I had changed.

Freebuff **does not keep chat history**, so there is no transcript for these sessions. What follows is what I asked about, reconstructed from my notes; the reasoning I ended up with is in the code and in the README.

Topics I asked about:

1. **What actually changes between `select()` and `poll()` inside the kernel**, and not just in the API. The answer that mattered: both mechanisms copy the user's interest set into the kernel on every call, register the thread on each socket's wait queue, sleep, rescan the whole set when something wakes, write the results back and unregister. Same algorithm, different representation. `select()` uses three bitmaps capped at `FD_SETSIZE` (1024) and destroys them as it goes, so the sets must be rebuilt from scratch every call; `poll()` uses one array of `struct pollfd`, has no such ceiling, and keeps the request (`events`) separate from the result (`revents`), so only the *interest* needs refreshing, not the whole structure.
2. **The cost model for the project.** `poll()` is O(number of watched descriptors) per call, not O(number of ready descriptors). Eight bytes per descriptor are copied in and eight back out, against roughly one bit per set for `select()`. That is the "still O(N)" claim in the README, and it is the reason `poll()` degrades like `select()` under many mostly-idle connections.
3. **The `events` / `revents` split, and what it does and does not let you skip.** `poll()` does not modify `events`, but it *does* overwrite `revents` on every call. This distinction is the one I had to get right in the comments — see section 4.3.
4. **Level-triggered semantics and why `POLLOUT` must be armed only while sending.** A socket with free send-buffer space is essentially always writable, so asking for `POLLOUT` while there is nothing to send turns the loop into a busy spin. `poll()` has no edge-triggered mode; `epoll` does, and that difference is part of why the two engines behave differently under the same workload.
5. **Which error bits the kernel reports regardless of the mask.** `POLLERR`, `POLLHUP` and `POLLNVAL` are always reported, even if you did not ask for them — the one behaviour that resembles "the kernel overwrote my mask".
6. **How the poll engine should implement the shared contract** so that it stays comparable with the select, epoll and io_uring engines: what the engine may do, what it must leave to the framework, and which counters it owns.
7. **The framework contract itself** — the meanings of `conn_is_reading()`, `conn_progress()`, `accept_ready()`, `conn_close()`, `udp_drain()` and the `loop_calls` / `sc_wait` counters, and how `POLLHUP` should be handled.

### 2.2 The implementation session

This is the session that produced the code. My prompt was a specification, not a blank "build this" request. The specification was:

- implement `int engine_run(server_t *s)` against the shared contract, and nothing else in the file — no sockets, no application logic, no statistics of my own;
- a `table_t` holding a `struct pollfd *` array and a parallel `conn_t **` array, allocated once with `calloc` at `max_clients + 1` and freed on exit;
- slot 0 is the listening socket, armed `POLLIN` for the life of the process; clients are appended at slot 1 onwards with `POLLIN`;
- before every `poll()`, rebuild each client's `events` from `conn_is_reading()` — `POLLIN` while reading, `POLLOUT` while sending, never both;
- on return, walk the array, and for every entry with non-zero `revents` call `conn_progress()`; if it returns non-zero, `conn_close()` the connection and remove it;
- removal by **swap-removal**: move the last entry into the vacated slot, decrement the count, and do not advance the index, because the entry that moved in still has to be handled in the same pass;
- serve the listener **after** the existing clients, so a new connection never inherits a stale `revents`;
- `EINTR` → continue the loop; a timeout → loop again;
- UDP: one `struct pollfd` for the listener, and the framework's `udp_drain()` when it is readable;
- count every `poll()` in `s->loop_calls` and `s->sc_wait`;
- no descriptor ceiling of its own — `poll()` has none, so the only limit is `--max-clients` and `ulimit -n`.

Codebuff wrote the file to that specification. What came back matched the specification closely; the file that ended up in the repository is that implementation with my corrections to it.

### 2.4 How I reviewed the generated code

I did not paste the draft into the repository and hope. Before accepting it I:

1. **Traced every path by hand** against the framework contract: accept → append → poll → ready client → `conn_progress()` → close → swap-remove → re-check slot *i* → accept. The path that matters most is the swap-removal, because an off-by-one there silently drops a connection's event.
2. **Checked every framework call against the other engines.** `conn_progress()`, `conn_close()`, `conn_is_reading()`, `accept_ready()`, `udp_drain()`, `server_ready()`, `stop_requested` — each one used the same way as in `select_server.c`, `epoll_server.c` and `io_uring_server.c`, so the four engines stay comparable. A grep of the finished file against those names is in section 6.
3. **Checked the counter contract.** `loop_calls` and `sc_wait` are incremented immediately before each `poll()`, in both the TCP and the UDP path, so poll's syscall cost lands in the same JSON summary as the other three engines.
4. **Checked the failure paths.** `EINTR` restarts the loop rather than being treated as an error; a `poll()` timeout is not an error; a full table rejects the new connection and counts it as `rejected` instead of overflowing the arrays.
5. **Checked that nothing outside the engine leaked in.** No socket calls, no `printf` in the loop, no allocations other than the two `calloc`s for the table, both freed on exit.

### 2.5 Where it was wrong

One thing worth recording: in an early session I asked whether `poll()` overwrites the caller's array the way `select()` overwrites its bitmaps, and the answer I was given conflated the two — it described the array as being destroyed and therefore needing to be rebuilt each iteration. That is `select()`'s behaviour. `poll()` leaves `events` alone and only overwrites `revents`. I caught it when the same claim appeared in a draft comment (see section 4.3) and checked it against `poll(2)` before keeping anything. The general lesson I took from it: for this project the *mechanism* has to be verified against the man page, not against an engineer's impression of it — and the same applies to generated code.

Each defines `const char *const ENGINE_NAME` and one `engine_run(server_t *s)`; each includes `framework.h` and nothing else from the project. - **The poll engine cannot build on its own.** `framework.h` is not committed in this repository. Verified:

  ```
  $ gcc -std=c11 -Wall -Wextra -c code/poll/poll_server.c -o /tmp/poll.o
  code/poll/poll_server.c:10:10: fatal error: 'framework.h' file not found
  ```

- **`poll` and `epoll` have no descriptor ceiling; only `epoll` avoids the O(N) per-call scan.** `select` is capped at `FD_SETSIZE` (1024) and has to reject anything at or above it, and it walks up to the highest descriptor number. `poll` has no such limit and scales with the number of connections rather than with the descriptor's number, but it still copies and scans the whole array on every call. `epoll` has no limit either and additionally keeps the interest set inside the kernel, so its per-call cost follows the number of *ready* descriptors. In all three readiness engines the user-space walk of the results is O(N).

The reason: the framework is Chirag's component, it changes under him, and a stale copy inside my folder would be a fork of someone else's code — exactly the coupling the project is trying to remove. ### 7.1 Errors caught in the earlier phase of the same component

Before the current framework-based rewrite, this component existed as a standalone `poll_echo_server.c` (Phase 1 of the project). That file was also built with AI assistance — Codebuff through Freebuff, DeepSeek V4 Flash — and the archive for it still exists in the git history. Four errors were caught and fixed there, and they are the reason I review AI output line by line rather than skim it:

1. **The swap-remove iterator bug.** The AI's first draft moved the last descriptor into the vacated slot but did not step the index back, so the loop advanced past the socket that had just been moved in and skipped its event. Caught by hand-tracing the array, fixed before any test was run.
2. **`signal()` and the infinite timeout.** With `timeout = -1`, glibc's `signal()` requests `SA_RESTART`, so `poll()` is restarted after the signal and the server never exits on Ctrl+C. Replaced with `sigaction()` and `sa_flags = 0`, so `poll()` returns `-1` with `errno == EINTR`. The claim was verified against `signal(7)` before the fix was accepted.
3. **Message-counter inflation.** The AI counted one message per successful `read()`. TCP has no message boundaries, so one client message split across two reads would count twice. The counter was changed to increment only when a whole echo buffer had been written back.
4. **Disarming `POLLIN` while waiting to send.** The suggested change would have stalled the pipeline under level-triggered `poll()`. Rejected; the design keeps `POLLIN` armed and masks `POLLOUT` only when data is queued.

### 10.1 Freebuff — session 1 (kernel behaviour)

> **You**
>
> I'm implementing the poll engine for a project that compares select, poll, epoll and io_uring at the syscall and wakeup level. Before I write anything: what actually changes between `select()` and `poll()` **inside the kernel**, not just in the API? And what does that mean for the cost of each call?

**Freebuff / Codebuff (DeepSeek V4 Flash):**

Both `select()` and `poll()` are *readiness* mechanisms, and the kernel-side algorithm is the same:

1. The kernel copies your interest set from user space into kernel space.
2. For each descriptor it asks the underlying object "are you ready?" and, if not, parks the thread on the object's wait queue.
3. The thread sleeps until one of them becomes ready.
4. The kernel walks the **whole set again**, builds the result and copies it back.

So the cost per call grows with the **size of the set**, not with the number of ready descriptors. That is the O(N) that bites at high connection counts.

The differences are in representation, not in mechanism:

| | select | poll |
|---|---|---|
| Interface | 3 bitmaps + `nfds` | array of `struct pollfd` |
| Ceiling | `FD_SETSIZE` = 1024 | none, only `RLIMIT_NOFILE` |
| Cost depends on | the **highest fd number** | the **number of entries** |
| Your input | destroyed — you must rebuild the sets | preserved — `events` and `revents` are separate fields |
| Bytes copied per fd | ~1 bit per set | 8 bytes in, 8 bytes out |

Two more things worth internalising: `poll()` is **level-triggered only** (no edge-triggered mode; `epoll` has one), and the kernel always reports `POLLERR`, `POLLHUP` and `POLLNVAL` whether or not you asked for them.

> **You**
>
> So the "you must rebuild it every time" argument only applies to select?
>
> For poll, what exactly does the kernel overwrite?

**Freebuff / Codebuff:**

Correct — the "rebuild everything" requirement is `select()`'s. `poll()` overwrites only `revents`; your `events` field is left exactly as you wrote it. The consequence is that you only have to refresh the *interest* of each entry (and only for entries whose direction changed), not reconstruct the whole structure.

Be precise about `revents`, though: because it is overwritten on every call, it is a per-call result, not a sticky state. You cannot read it in the next iteration and conclude "this was still ready".

> **You**
>
> And `POLLOUT` — I've seen people get this wrong.

**Freebuff / Codebuff:**

Arming `POLLOUT` permanently is the classic mistake. A socket with free space in its send buffer is *always* writable, so `poll()` returns it on every single call and the loop spins at 100% CPU doing nothing. Level-triggered means "report while the condition holds". So: arm `POLLOUT` only while there is something to send, and arm `POLLIN` only while you are waiting to read. Never both at once.

### 10.2 Freebuff — session 2 (the framework contract)

> **You**
>
> The engine has to implement a shared contract: `engine_run(server_t *s)`, plus `conn_t`, `conn_is_reading()`, `conn_progress()`, `conn_close()`, `accept_ready()`, `udp_drain()`, `server_ready()`, `stop_requested`, `WAIT_MS`, `s->config->max_clients`, and counters `s->loop_calls` and `s->sc_wait`. What should the poll engine do, and what must stay in the framework?

**Freebuff / Codebuff:**

The engine's job is narrow: *wait, and decide which socket can make progress*. The framework owns the state machine and the bytes.

Concretely, for poll:

- Keep a `struct pollfd` array and a parallel array of `conn_t *`. `poll()` needs a contiguous array, and the framework's connection object cannot live inside it, so they go side by side and index *i* means the same connection in both. Looking up the connection for a ready entry is then O(1) instead of a search.
- Reserve slot 0 for the listening socket, armed `POLLIN` for the life of the process. Clients start at slot 1. Every new client is appended with `POLLIN`, because a client always begins by reading a request header.
- Before each `poll()`, refresh each client's `events` from `conn_is_reading()`: `POLLIN` while reading, `POLLOUT` while sending. Never both.
- After `poll()` returns, walk the array and for every entry with non-zero `revents` call `conn_progress()` — that is where the single `recv()` or `send()` happens. `conn_progress()` returning non-zero means the connection is finished: call `conn_close()` and remove it.
- Remove with **swap-removal**: move the last entry into the hole and decrement the count. Shifting would be O(N) per disconnect, and poll does not care about order. Do not advance the index after a swap — the entry that moved in still has to be processed in this same pass.
- Handle `EINTR` by continuing the loop (the framework's `stop_requested` flag is what the signal handler sets), and treat a timeout as "loop again".
- Serve the listener **after** the existing clients, so a freshly accepted connection can never inherit a stale `revents`.
- UDP has no per-client sockets: poll one descriptor for the listener and hand the datagrams to `udp_drain()`.
- Count every `poll()` in `loop_calls` and `sc_wait`, so poll's syscall cost shows up in the same JSON summary as the other engines.

> **You**
>
> One more thing — `poll()` and the `revents` mask. Is the array "overwritten by the kernel"?

**Freebuff / Codebuff:**

Not the array — only one field of each entry. The kernel overwrites **`revents`**; your `events` field is left untouched, which is the whole difference from `select()`.

If someone tells you the `pollfd` array is destroyed and has to be rebuilt from scratch every iteration, that is `select()`'s behaviour, not `poll()`'s.

```c
/*
 * poll_server.c - the poll engine.
 * Only the event loop lives here; see Chirag/code/common/framework.h for the contract.
 *
 * poll has no descriptor-number ceiling, but the whole pollfd array still
 * crosses into the kernel and is scanned on every call: also O(N).

#define _GNU_SOURCE
#include "framework.h" /* Chirag/code/common/framework.h; the Makefile adds -I */

#include <errno.h>
#include <poll.h>
#include <stdlib.h>

const char *const ENGINE_NAME = "poll";

typedef struct table_t {
    struct pollfd *fds;
    conn_t **clients;
    size_t count;
    size_t capacity;
} table_t;

static int remember(server_t *s, conn_t *c, void *context)
{
    table_t *table = context;
    if (table->count == table->capacity) {
        s->rejected++;
        s->accepted--;
        conn_close(c, 0);
        s->closed--;
        return 0;
    }
    table->clients[table->count] = c;
    table->fds[table->count++] = (struct pollfd){.fd = c->fd, .events = POLLIN};
    return 0;
}

static int run_udp(server_t *s)
{
    server_ready(s);
    while (!stop_requested) {
        struct pollfd item = {.fd = s->listener, .events = POLLIN};
        s->loop_calls++;
        s->sc_wait++;
        int n = poll(&item, 1, WAIT_MS);
        if (n < 0) {
            if (errno == EINTR) {
                continue;
            }
            return -errno;
        }
        if (n > 0) {
            int rc = udp_drain(s);
            if (rc < 0) {
                return rc;
            }
        }
    }
    return 0;
}

int engine_run(server_t *s)
{
    if (s->config->transport == TRANSPORT_UDP) {
        return run_udp(s);
    }
    table_t table = {.capacity = s->config->max_clients + 1, .count = 1};
    table.fds = calloc(table.capacity, sizeof(*table.fds));
    table.clients = calloc(table.capacity, sizeof(*table.clients));
    if (!table.fds || !table.clients) {
        free(table.fds);
        free(table.clients);
        return -ENOMEM;
    }
    int result = 0;
    table.fds[0] = (struct pollfd){.fd = s->listener, .events = POLLIN};
    server_ready(s);
    while (!stop_requested) {
        for (size_t i = 1; i < table.count; i++) {
            table.fds[i].events = conn_is_reading(table.clients[i]) ? POLLIN : POLLOUT;
        }
        s->loop_calls++;
        s->sc_wait++;
        int n = poll(table.fds, table.count, WAIT_MS);
        if (n < 0) {
            if (errno == EINTR) {
                continue;
            }
            result = -errno;
            break;
        }
        if (!n) {
            continue;
        }
        for (size_t i = 1; i < table.count;) {
            if (!table.fds[i].revents) {
                i++;
                continue;
            }
            int rc = conn_progress(table.clients[i]);
            if (rc) {
                conn_close(table.clients[i], rc);
                table.count--;
                table.fds[i] = table.fds[table.count];
                table.clients[i] = table.clients[table.count];
            } else {
                i++;
            }
        }
        if (table.fds[0].revents & POLLIN) {
            result = accept_ready(s, remember, &table);
            if (result < 0) {
                break;
            }
        }
    }
    free(table.fds);
    free(table.clients);
    return result;
}
```

> Let me check this. Walk me through the disconnect path step by step — the `conn_progress()` call, the swap, and what happens to the index. I want to trace it by hand.

**Freebuff / Codebuff:**

Take the case where client at slot 3 has closed and `table.count` is 7.

1. `conn_progress(table.clients[3])` performs the I/O and returns non-zero — the connection is finished.
2. `conn_close(table.clients[3], rc)` tells the framework the connection is done; the framework accounts for it and closes the descriptor.
3. `table.count--` → 6. The array is now logically 6 entries, 0..5, and slot 6 is dead.
4. `table.fds[3] = table.fds[6]` and `table.clients[3] = table.clients[6]` copy the **last** entry into the hole. The client that was at slot 6 is now at slot 3. No shifting, so removal is O(1).
5. The index `i` is **not** advanced. Slot 3 now holds a different client, and that client's `revents` came from the same `poll()` call, so it still has to be checked in this pass. Advancing `i` here would skip it for one iteration — it would be picked up on the next `poll()`, but it would have been waiting in the meantime.

The loop condition is `i < table.count`, so once the last slot is removed the loop ends correctly.

> **You**
>
> And the `revents` check — should I be decoding `POLLHUP` and `POLLERR` here?

**Freebuff / Codebuff:**

No, and this is worth being deliberate about. `POLLHUP` can arrive **together with** readable data: a peer that sends its last bytes and closes gives you `POLLIN | POLLHUP` in the same `revents`. If you treat the hang-up as "the connection is dead" and close immediately, you throw away data that was already in the buffer.

So do what the framework expects: treat *any* non-zero `revents` as "this descriptor may have made progress", call `conn_progress()`, and let the result of the actual `recv`/`send` decide what happened — 0 bytes means the peer closed, a negative errno means an error. `POLLERR` and `POLLNVAL` are reported whether or not you asked for them, but they also show up as a failed `recv`/`send`, so the same rule covers them.
