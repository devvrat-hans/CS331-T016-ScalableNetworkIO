# AI Contribution and Verification

## Scope of AI Contribution

AI contributed substantially to the documentation and presentation workflow of the project.

The AI tools were used for:

- Technical learning.
- Understanding the project requirements.
- Reviewing team source code.
- Generating report drafts.
- Generating and revising LaTeX.
- Generating and reviewing PPT content.
- Interpreting benchmark results.
- Suggesting graphs and tables.
- Generating plotting code.
- Reviewing the report and PPT.
- Improving technical explanations and wording.

In some stages, an initial complete draft of a report or presentation was generated by AI. These drafts were then treated as working drafts rather than final submissions.

---

## What Was Provided by the Student/Team

The AI models were provided with project-specific material such as:

- The project description and expected outcomes.
- The required PPT structure.
- The source code produced by team members.
- Benchmarking files and measured results.
- Existing report/PPT drafts.
- Formatting requirements.
- Feedback and observations from team members.
- Required changes and corrections.

The project-specific implementation and benchmark measurements were therefore not assumed from general AI knowledge.

---

## Verification of Technical Explanations

AI-generated explanations were verified in several ways.

### Source-code verification

Implementation-specific statements were compared against the actual code.

For example, the final report discusses specific implementation behavior such as:

- `select` rebuilding descriptor sets and having the `FD_SETSIZE` limitation.
- `poll` using a dynamically sized descriptor array while retaining repeated O(N) scanning.
- `epoll` using a persistent interest list and returning ready descriptors.
- `io_uring` using submission and completion queues.
- The one-outstanding-operation-per-client limitation in the current io_uring implementation.

These details were checked against the corresponding implementations before being included.

### Benchmark verification

Numerical values were checked against the actual benchmark results.

Examples include:

- Throughput at 10, 100, and 1,000 connections.
- Mean latency.
- System calls per message.
- Event-wait calls per message.
- CPU utilization.
- Peak RSS.
- Latency percentiles from the supplementary profiling run.

AI was used to help interpret the values, but the measured data itself came from the team's benchmark and profiling runs.

### Team verification

Where an implementation-specific detail was unclear, the relevant team member was consulted.

This was especially important because responsibility for the four server implementations was distributed across the team.

### Documentation verification

Technical concepts were cross-checked against Linux documentation and relevant documentation for the technologies being used when necessary.

### Execution and compilation

The generated LaTeX and associated plotting/material-generation code were compiled or executed to check whether the resulting artifacts actually worked.

Errors identified during this process were corrected before the final version was prepared.

---

## Verification of Graphs

AI-generated plotting code was not treated as proof that the resulting figure was correct.

The generated plotting code was executed using the actual project data.

The resulting figures were manually checked for:

- Correct data source.
- Correct mechanism names.
- Correct connection counts.
- Correct units.
- Correct axis labels.
- Consistency with the underlying values.
- Consistency between the graph and its written interpretation.

---

## Handling Incorrect or Over-General AI Output

AI-generated responses were sometimes broader than the actual implementation or suggested conclusions that were stronger than what the data supported.

When this happened, the content was revised or rejected.

A major example was avoiding the simplistic conclusion that io_uring was universally faster than epoll.

The measured results showed that io_uring had a major advantage in normalized syscall frequency, but epoll was sometimes slightly ahead in raw throughput on the tested workload. The final report therefore presents io_uring's syscall reduction as the strongest architectural result instead of claiming an unconditional throughput victory.

This distinction is explicitly reflected in the final report. 

---

## Separation Between Measured Results and AI Interpretation

Measured data and AI-generated interpretation were treated differently.

Measured results:
- Taken from benchmark/profiling output.
- Used as the numerical basis for tables and graphs.
- Checked before incorporation.

Interpretation:
- AI helped explain trends and suggest possible reasons.
- Explanations were checked against the implementation and experiment.
- Unsupported explanations were removed or weakened.

This distinction was especially important for CPU, memory, latency-percentile, and syscall observations because these were generated through different measurement procedures.

---

## Student's Final Responsibility

The student was responsible for:

- Supplying the project context and project files.
- Deciding which information was relevant.
- Comparing outputs from different AI models.
- Checking generated explanations against code and measurements.
- Discussing implementation details with teammates.
- Running/compiling generated material.
- Selecting the useful graphs and tables.
- Editing the final report.
- Editing the final PPT.
- Deciding which AI suggestions to accept, reject, or modify.
- Ensuring that the final conclusions were supported by the actual project evidence.

Therefore, AI was used as an assistant in the project workflow rather than as an unquestioned source of technical truth.

---

## Summary

The AI-assisted process followed a draft → verify → revise model.

AI was used to accelerate understanding, organization, drafting, analysis, and formatting. The final material was then reviewed against the team's implementation, benchmark results, documentation, and project requirements.

The final report and presentation therefore represent a combination of:

- Team-generated implementation and experimental work.
- Student-led technical review and decision-making.
- AI-assisted analysis, drafting, and presentation preparation.
